## 1. 产品愿景

构建一套高精度、可维护的字体反混淆中间件系统（Font De-Obfuscation Engine, FDE），使个人用户能够对自己购买的知乎会员内容进行本地备份与无障碍阅读。系统以**服务端微服务**形态运行，通过多级识别方案级联，实现 ≥99.5% 的文字还原准确率。

## 2. 问题陈述

### 2.1 当前痛点

| # | 痛点 | 影响 |
|---|------|------|
| 1 | 知乎会员页字体混淆已升级至 L2（字形扰动）+ L3（动态子集），浏览器端像素比对方案精度不足 | 文字提取不完整，部分字符显示异常 |
| 2 | 每次请求的字体文件完全唯一，码点映射随机化 | 无法缓存复用映射表，每次都需重新解析 |
| 3 | 字体请求携带 Session 绑定 Token，不可独立获取 | 拦截字体文件需要挂钩页面会话 |
| 4 | 现有 zhfont 方案（浏览器端纯 Canvas 比对）准确率仅 ~90% | 未达可用标准 |

### 2.2 知乎混淆机制演进

```
Phase 1 (L1 · 已淘汰): cmap 码点替换 —— 仅修改码点→字形映射，字形轮廓不变
Phase 2 (L2 · 部分残留): 字形扰动 —— 轮廓控制点加入随机偏移量
Phase 3 (L3 · 当前主力): 动态子集 —— 每次请求生成唯一字体文件，码点映射完全随机
当前: L2 + L3 组合
```

### 2.3 为什么浏览器端方案不可行

- 渲染分辨率受限，笔画细节丢失，形近字误识率高
- 字形扰动使像素 Hash（pHash）偏移，无法精确匹配
- 依赖浏览器环境，无法水平扩展
- 处理速度 50~200ms/字，批量处理明显瓶颈

## 5. 功能需求

### 5.1 方案优先级级联（核心流程）

```
请求进入
  │
  ├─→ [Step 1] 方案 D（API 直取）
  │     └─ 若可用 → 直接返回纯文本（最高优先级，零成本）
  │
  ├─→ [Step 2] 拦截 woff2 字体文件
  │
  ├─→ [Step 3] 方案 B（字体逆向 · 主力）
  │     ├─ 轮廓 Hash 精确匹配 → 置信度 1.0
  │     └─ KD-Tree 最近邻匹配 → 相似度评分
  │
  ├─→ [Step 4] 方案 C（CNN 分类器 · 高速兜底）
  │     └─ 仅处理方案 B 未覆盖的字形
  │     └─ 置信度阈值 θ = 0.95
  │
  ├─→ [Step 5] 方案 A（OCR 兜底 · 最终保障）
  │     └─ 仅处理置信度 < θ 的字形
  │     └─ 预期触发率 < 1%
  │
  └─→ [Step 6] 汇总映射表，替换混淆文本
```

### 5.2 功能模块

| 模块 | 功能 | 输入 | 输出 |
|------|------|------|------|
| **HTTP 拦截代理** | 拦截 woff2 字体请求与页面响应 | 页面 URL | woff2 字节流 |
| **Font Reverser** (方案 B) | 轮廓 Hash 匹配，还原字形映射 | woff2 字节流 | `{混淆码点 → 真实字符}` |
| **Glyph Classifier** (方案 C) | CNN/ViT 字形图像分类 | 字形图像 64×64 | Top-3 预测 + 置信度 |
| **OCR Fallback** (方案 A) | 截图 + PaddleOCR 兜底 | 字符截图 | 识别文本 |
| **Pipeline Orchestrator** | 流程调度、置信度阈值、降级 | 任务配置 | 汇总映射表 |
| **Mapping Cache** (Redis) | 字体 Hash → 映射表缓存 | 字体 Hash | 映射表 |
| **Drift Detector** | 混淆策略变化检测与告警 | 统计指标 | 告警 / 触发重校准 |
| **Admin Dashboard** | 监控、统计、手动校正 | — | Web UI |
| **REST API** | 对外服务接口 | 页面 HTML + woff2 | 还原文本 + 准确率估算 |

### 5.3 方案 B 详细需求：轮廓归一化

- 提取字形全部轮廓点坐标 (x, y) 及标志位 (on/off-curve)
- 按 x/y 范围映射到 [0, 100] 单位空间
- 坐标量化精度：round(value, 1)，过滤 ±3 单位扰动噪声
- 序列化为规范化字符串，计算 MD5 作为轮廓 Hash
- 精确 Hash 匹配失败时，退回到 KD-Tree 最近邻搜索（欧氏距离容差 ε = 2.5）
- 匹配结果置信度 ≥ 0.95 即采纳

### 5.4 方案 C 详细需求：字形分类器

- 模型：ViT-Tiny（推荐）或 MobileNetV3-Small
- 输入：64×64 灰度字形图像
- 输出：分类结果 + Top-3 置信度
- 训练数据：6763 字 × 50 字体 × 多字号 ≈ 340 万样本
- 数据增强：轻微仿射变换、高斯噪声、亮度抖动
- 专项数据：从知乎实际获取的混淆字形样本

### 5.5 方案 A 详细需求：OCR 兜底

- 驱动：Playwright（Chromium）保证字体完整渲染
- OCR 引擎：PaddleOCR v4
- 优化：需兜底字符聚合为一张大图批量处理
- 实例池复用（pool_size = 4）
- 单字超时 3s 标记为低置信度

### 5.6 参考字库需求

| 字库范围 | 字符数 | 说明 |
|----------|--------|------|
| GB2312 一级汉字 | 3755 | 最常用，必须覆盖 |
| GB2312 二级汉字 | 3008 | 常见于专业文章 |
| CJK 扩展 A 部分 | ~500 | 人名、地名用字 |
| 标点与符号 | ~200 | 全角标点、特殊符号|
| **合计** | **~7500** | |

参考字体来源：思源黑体 SC、思源宋体 SC、方正系列等 10+ 款字体。

## 9. 风险与约束

### 9.1 技术风险

| 风险 | 概率 | 影响 | 应对 |
|------|------|------|------|
| 知乎增大字形扰动幅度 | 高 | 方案 B 命中率下降 | 动态调整 tolerance；KNN 容差自适应 |
| 混淆引入非线性变换 | 中 | 方案 B 完全失效 | 方案 C+A 可独立兜底，准确率仍 >97% |
| 字体请求增加额外签名 | 中 | 无法获取字体 | 浏览器插件注入方案绕过 |
| ViT 模型过拟合已知字体 | 低 | 新字体泛化差 | 持续收集新字体样本，季度重训 |

### 9.2 合规约束

1. 使用前须评估目标平台服务条款
2. 仅在个人已购买会员内容的范围内使用
3. 不公开发布可直接运行的完整代码
4. 发现漏洞先向平台方负责任披露，给予 90 天修复期

### B. 术语表

| 术语 | 定义 |
|------|------|
| FDE | Font De-Obfuscation Engine，本系统全称 |
| woff2 | Web Open Font Format 2，知乎动态下发的字体格式 |
| 字形混淆 | 对字体文件中字符轮廓或码点映射关系进行随机化处理 |
| L1 级混淆 | cmap 替换，仅修改码点→字形映射，字形不变 |
| L2 级混淆 | 字形扰动，轮廓控制点坐标加入随机偏移量 |
| L3 级混淆 | 动态子集，每次请求生成不同字体子集文件 |
| 轮廓 Hash | 对字形矢量路径归一化后计算的几何指纹 |
| 置信度 | 分类器对预测结果的概率分值 |
